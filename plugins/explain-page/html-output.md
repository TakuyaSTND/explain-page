# 人に見せる出力の作り方（HTML／用語ホバー）

エージェントが人に見せる説明・報告・判断の頁を作るときの決まりです。前半は頁を書く人（エージェント）向けの決まり、後半の「Hookが組み合わせる説明component」はフックが指示文に組み込む部品ごとの説明です。
用語の言い回しは、共通の用語集 `glossary-shared.md` とプロジェクト固有の `.claude/glossary.md` を正本にします。固有のほうが共通を上書きします。

## 何のためか

**目的は読み手のわかりやすさ**です。長い出力ほど読みにくいので、長さは頁にする正しい合図です。費用を理由に図や表を減らす方向へは動かしません。閾値は、使う人が明示的に上げたときだけ上げます。

## 満たすこと（差し戻しの判定基準）

1. **判断を戻す口**：相手に何かを決めさせるなら、選択肢を実際の入力部品（radio／checkbox／number）にし、**選ぶと貼り返す依頼文が組み上がる** `<pre>` とコピーボタンを置きます。クリップボードが使えない環境のために「全部選ぶ」も添えます。依頼文は固定の形です（1行目「【頁の回答】頁の題」、問いごとに「Q1. 問い: 選んだ案」、答えていない問いは「(未選択 = お任せ＝推奨で進める)」、最後に「---」と締めの1文）。選択肢には `pros`（利点）・`cons`（代償）を添え、推奨でない案にも選ぶ理由を書きます。見た目の違う案には `thumb` で小さな絵を付けられます。
2. **判定には異議の口**：こちらが下した判定（評価・分類・合否など）を並べるなら、**1件ずつ「これは違う」を押せる形**にします。押したものが依頼文に「異議. 対象: 理由」として並ぶようにします。判定が一方通行だと、誤りを正す手段が文章の書き直ししか無くなるためです。
3. **出所を構造で分ける**：〈実測〉〈仮定〉〈推奨〉〈一次〉のラベルを付け、散文に混ぜません。
4. **長い詳細は `<details>` で折りたたむ**：決めるのに要る情報を埋もれさせません。
5. **難しい用語にホバー説明**（次の節）。
6. 色は必ずトークン（`--変数`）で定義し、明暗の切り替えの中だけで色を決めません。`body` には背景色を明示します。文字と背景のコントラストは、小さな字で4.5以上を目安にします。
7. **対話部品を入れたら、動きを実際に確かめる**（読むだけの頁なら不要）。

## 用語ホバーの原則

### 積極的に包む

**迷ったら包みます。** 専門用語・略語・そのプロジェクト固有の語は、読み手が知らない前提で扱います。**用語集に無ければ足します**（1行足せば次から使えます）。

### 変数名・識別子も網羅する

`status`・`retry_count` のような**コードの中の名前**を本文に出すなら、**必ずホバーを付けます**。読み手はその名前を見たことがないので、付けないとそこで読むのが止まります。

- よく出る識別子は、用語集に節を作ってまとめておきます。
- 用語集に無い識別子を出すなら、**その場で1行足します**。
- 説明には**具体例か取りうる値**を入れます。例＝〈`status`＝処理の状態。待ち／実行中／完了〉。

### 説明は噛み砕く

**専門語で専門語を説明しません。**

| やること | 具体的に |
|---|---|
| 一文を短く | 1文に「かつ」「ただし」を2つ以上入れない。切る |
| 主語を書く | 「誰が」「何が」を省かない |
| 数字に単位と分母 | 「2.4倍」でなく「トークンが2.4倍（同じ内容を別の形で書いた場合と比べて）」 |
| 例を1つ付ける | 抽象語だけで終わらせない |
| 記号を開く | 〈∴〉〈＝〉を多用しない。「だから」「つまり」と書く |
| 先に結論 | 段落の1文目に結論。理由は後 |

### ただし機械的に当てはめない

**辞書にある語を本文から機械で全置換しません。** 同じ語に何度もホバーが付くと読めなくなり、直前に言い換えた語には説明が要らず、見出しや表の中で包むとレイアウトが崩れるためです。

| | 指針 |
|---|---|
| 包む | その頁で**初めて出た**難しい語／読み手の判断に直接効く語／誤解されると結論が変わる語 |
| 包まない | 2回目以降の同じ語／直前に平易に言い換えた語／見出しの中／表のヘッダ |
| 足す | 用語集に無い難しい語を使ったとき（その場で1行足す） |

### 機械にやらせるのは「一致」と「育ち」だけ

`.claude/scripts/check_gloss.py <html>` を表示の前に通します。見るのは4つです。

0. **取りこぼし**（要修正）：説明は付いているが、包んだ語を読み取れず、一致の検査を受けていない。
1. **一致／相違**（相違は要修正）：用語集にある語を包んだ説明が正本と合うか。正本の説明に頁の文脈を足すのはよい。
2. **育ち**（足す候補）：包んだ語が用語集に無い。プロジェクト固有の候補として示すだけで、自動では書かない。
3. **参考**（強制しない）：用語集にある語が本文にあるのに一度も包んでいない。包まない判断も正当なので、機械はここで止めない。

## 頁はレンダラーで組む

**手書きの HTML は、この文書の基準を満たしていても検品が通りません。** 検査器（`.claude/hooks/visual/artifact_inspection.py`）は正規のレンダラー（`.claude/hooks/visual/render_components.py`）の出力を前提にしていて、次を見ます。

- 部品の目印＝`data-component="overview"` などの属性（見出しの文字では検出しない）
- 頁の中の script＝承認済みの1本だけ
- 根拠の欄の各行＝出所の属性（3列でも属性が無ければ「出所欠け」になる）

使い方は、定義JSONを1枚書いて次を走らせるだけです。

```
python .claude/scripts/render_page.py <定義.json>
```

道具が承認済みの置き場に「完全版」と「器用」を書き、検品と表示検査をその場で回します。**公開に渡すのは器用のほう**です（完全版は完全な1文書なので、公開の器に入れると入れ子になります）。

**箱と矢印の図**は `diagram` に箱と矢印を宣言します。配置と経路はレンダラーが計算します。

```
"diagram": {"nodes": [{"id":"a","title":"依頼"},{"id":"b","title":"返事"}],
            "edges": [{"from":"a","to":"b","label":"組む"}]}
```

**生の SVG はそのままは受け取りません。** 手書きの SVG は `svg` の部品に渡すと、許可リストで組み直してから載せます。図の中には用語のホバーを置けないので、図に出した用語は本文で説明します。

**横並び**は、節の中の塊に `columns`（2〜4段）か `tiles`（折り返し）を書きます。狭い画面では自動で1列に畳みます。

```
"columns": [{"heading":"以前","text":"…"},{"heading":"いま","text":"…"}]
"tiles":   [{"title":"2段組み","text":"横に並べる","tone":"good"}]
```

**頁全体の2段組み＝側柱**は、`content` に `rail` を足します。広い画面では本文の右に、狭い画面では見出しの直後に来ます。`{"heading":"目次","toc":true}` を入れると節の見出しから目次を自動で組み、いま読んでいる節を光らせます。`{"heading":"この頁の用語","glossary":true}` で、頁に2回以上出た用語の一覧を出します。側柱は節ではない（部品の目印を持たない）ので、横に置いてよいのは添え物だけです。

**見出しと中身のずれ**は機械で止めます（別の部品が持つ言葉を見出しに借りた・節の中身が空・見出しの重複・番号の重複）。意味が噛み合っているかまでは見ていません。

**大きい頁の耐荷重**は `.claude/scripts/stress_page.py` で測れます。合成の節を並べて目標のバイト数まで膨らませ、そのまま検品と表示検査を通します。

⚠️用語集の語とコード片がぶつかることがあります。本文に用語集の語をコード書きで出すと、包んでいない用語と判定されて検品が落ちることがあるので、本文では日本語に開きます。

## 正本は Markdown・見え方は HTML

| 何を | どの形で | 理由 |
|---|---|---|
| エージェントが常に読む指示（`CLAUDE.md`・`AGENTS.md` など） | **Markdown** | 常に読み込むのでトークンが効く。差分が読める |
| 人が理解・比較・承認するもの（状況の報告・提案・判断の頁） | **HTML** | 比べる・触る・決めるができる |
| HTML から取り出した決定（依頼文・並び順・差分） | **Markdown / JSON** | コミットするのはこちら。HTML 自体は追跡しない |

作業の頁はリポジトリに入れず、一時フォルダの承認済みの置き場に置きます。外部への公開は、人の明示の承認があるときだけにします。

## Hookが組み合わせる説明component

componentは排他的なmodeではない。必要なものを同じ説明へ複数入れる。

<!-- HOOK_STYLE:START -->
本文を全部同じ文字サイズ・太さ・色で並べない。見出しは本文と別のfont系統または明確なsize差を使い、Goal・Risk・Decisionなどの短いlabelは太字にする。意味のある色は役割を固定して使い、装飾のためだけに色を増やさない。重要なflowや比較は文字列だけでなくstep・badge・table・noteなど、内容に合う構造で視覚的に分ける。色はCSS tokenで定義し、body背景を明示する。Zen Old Mincho／Zen Kaku Gothic New／IBM Plex Monoの役割分担を参考にしつつ、localにあるfontとfallbackだけで組む。font・script・画像を外部URLから読み込まない。OSの明暗設定に加えて `data-theme="light|dark"` でmanual theme overrideできるようにする。backtickはsafeなinline codeとして `<code>` にし、raw HTMLはescapeする。注意・警告はwarn tone、反例・失敗はbad tone、確認済みはgood toneに分ける。表の補足はcaption、数値はnumeric cellで桁を揃える。頁末には非機密のprovenance footerを置く。対話部品を置いたらbuild等のlogicを実際に走らせる。preview時に実browserのvisual smokeを行い、desktopと390px mobileの横overflow、JavaScript error、tooltip、decision interactionを検査する。
<!-- HOOK_STYLE:END -->

<!-- HOOK_COMPONENT:overview:START -->
最初に「一言でいうと」を置き、Goal / Now / Changed / Risk / Decisionを平易に示す。判断が無ければ「判断不要」と書ける。
<!-- HOOK_COMPONENT:overview:END -->

<!-- HOOK_COMPONENT:walkthrough:START -->
ユーザーをそのProjectの初心者として扱う。いきなり仕組みへ入らず、変更前は何が起きていたか、何が困りごとか、なぜ今直すのか、放置すると誰にどう影響するかを先に説明する。その後で入力、処理、結果、なぜその設計が必要かをstep-by-stepで示し、Project固有の前提を省略しない。
<!-- HOOK_COMPONENT:walkthrough:END -->

<!-- HOOK_COMPONENT:examples:START -->
重要な抽象概念ごとに、Project文脈の具体例を少なくとも1つ置く。入力→途中の動き→結果、またはBefore/Afterで変化を見せる。正しい例だけでなく「この場合は違う」という反例、重要な誤解、例外も添える。
<!-- HOOK_COMPONENT:examples:END -->

<!-- HOOK_COMPONENT:summary:START -->
長い説明の上部にGoal / Now / Changed / Risk / Decisionの案内板を置き、その直後に別置きの3行summaryを置く。summaryは案内板であり、walkthroughやdetailsを削除しない。
<!-- HOOK_COMPONENT:summary:END -->

<!-- HOOK_COMPONENT:progress:START -->
複数Agentや長い作業は、Needs You / Failed / High Risk / Working / Completedを分け、人待ちと失敗を先に見せる。
<!-- HOOK_COMPONENT:progress:END -->

<!-- HOOK_COMPONENT:visual:START -->
比較、関係、処理flow、timeline、Before/Afterを図で示す。図だけで終えず、読み方と意味を文章でも説明する。
<!-- HOOK_COMPONENT:visual:END -->

<!-- HOOK_COMPONENT:decision:START -->
人の選択・承認が本当に必要な時だけ、radio/checkbox/number等を置き、各選択肢の推奨有無と理由を表示する。選ぶと貼り返す依頼文が組み上がる `<pre>`、コピーボタン、clipboard不可時の「全部選ぶ」を付ける。こちらが判定を並べる頁では1件ずつ「これは違う」を押せるcheckboxに加え、自由記述の異議欄も付ける。decision必須planではinput / pre / copy / select-all / 異議UIが実体にあることをreceiptのGateで検証する。記録・解説だけならdecisionは要求しない。
<!-- HOOK_COMPONENT:decision:END -->

<!-- HOOK_COMPONENT:evidence:START -->
確認済み事実、実測、仮定、推奨、一次、未検証、blockerをbadgeやtableで構造的に分ける。Evidence tableは「種類／内容／どこで確かめたか」の専用3列にし、各行のsource列を空にしない。重要なclaimにはURLではなくても再現可能なlocal evidence path（例：`path/to/file.py:123`、test command、receipt hash）を付ける。source欠落はreceiptのGateで拒否する。
<!-- HOOK_COMPONENT:evidence:END -->

<!-- HOOK_COMPONENT:glossary:START -->
初出の専門語・略語・Project固有語・code identifierは、やさしい言い換えの後に元の専門語を添える。重要語の初出は `<span class="t" tabindex="0" data-d="正本の説明" aria-label="語：正本の説明">語</span>` で包み、hoverとkeyboard focusの両方で説明を出す。説明は共通＋Project用語集の正本と一致させ、preview前に `.claude/scripts/check_gloss.py <html> --strict` を通す。code identifierなら「何を入れる／何をする／何が返る」を1文で説明する。`<code>` 内のcamelCase / snake_case / ALL_CAPS等を抽出し、用語集に無いものはProject固有候補、用語集にあるのに未包装のidentifierは未包装エラーとしてreceiptのGateで拒否する。辞書の全語を機械的に包まず、その頁の理解に必要な語の初出を優先する。
<!-- HOOK_COMPONENT:glossary:END -->

<!-- HOOK_COMPONENT:details:START -->
test、diff、log、長い根拠は `<details>` へ畳めるが、理解に必要な説明そのものは隠さない。
<!-- HOOK_COMPONENT:details:END -->
